### M2 · 企业级架构骨架（百人并发 / 万人容量）

**目标**：让单实例能扛 100 并发、长期能支撑 10000 注册用户。

**异步队列**
- `app/queue/asyncio_queue.py`：通用 asyncio.Queue 封装
- `app/queue/handlers.py`：LLM 调用 / 评测任务 / 知识库入库
- 生产端 API 调用入队 → 后台 worker 消费

**限流**
- `app/ratelimit/sliding_window.py`：Redis Lua 脚本实现的滑动窗口
  - 全局 token 桶：100 QPS
  - 每用户 token 桶：10 QPS
  - 每 IP token 桶：20 QPS
- 超限返回 429 + Retry-After

**连接池**
- `app/database.py`：asyncmy pool（pool_size=20, max_overflow=40）
- `app/redis_client.py`：redis.asyncio + 连接池 + Sentinel 接入

**多实例**
- gunicorn -k uvicorn.workers.UvicornWorker -w 4
- 共享 Redis 做会话（已有）

**压测**
- `bench/stress_test.py`：locust 脚本，模拟 100 用户并发完整模拟面试
- 报告：RPS / P50 / P95 / P99 / 错误率

**测试**
- `tests/test_ratelimit.py`：高 QPS 请求 → 429
- `tests/test_queue.py`：任务入队 → 后台消费 → 完成回调

**文档**
- `docs/M2-企业级架构.md`（含压测数据）

### M4 · 出题 + 追问 LLM-as-judge 评测

**目标**：定量评估 Agent 的出题质量与追问深度。

**Judge 设计**
- LLM-as-judge：用 DeepSeek 给「出题」与「追问回复」打 1-5 分
- 多维度评分：
  - **相关性**：题目是否对应简历/岗位核心能力
  - **难度适宜**：与候选人级别匹配（不超纲/不偏易）
  - **答案点覆盖**：标准答案的关键点是否被题目考察到
  - **追问深度**：追问是否问到关键细节（不是「还有呢」式空问）

**评测集**
- 30-50 条样本（手工 + LLM 生成）
- 每样本含：岗位描述、简历、出题、追问回复、参考答案、维度分数

**脚本**
- `bench/question_eval.py`：调 LLM 出题 + LLM-as-judge 打分
- `bench/followup_eval.py`：追问链路评测
- `bench/judge_accuracy.py`：用 20 条人工标注文本验证 Judge 一致性

**成本控制**
- max_tokens=512（评分不需要长文本）
- 评测集 30 条 + Judge 校验 20 条 ≈ 0.3-0.5 元

**文档**
- `docs/M4-出题与追问评测.md`（含 Judge 一致性数据）

## 四、风险与决策点

**风险 1：DeepSeek key 余额 10 元**
- 控制：所有 LLM-as-judge `max_tokens=512`，单次调用不超过 ¥0.002
- 监控：每轮报告后余额预估（剩余 / 总）
- 触发：若低于 3 元，本轮 M4/M5 暂停询问

**风险 2：WebSearch 抓取受网络/版权限制**
- 兜底：优先 CC 协议 / 政府公开报告 / 学术开放资源
- 不可用时：用户提供的子学科可用本地 docx 占位

**风险 3：LLM-as-judge 与人工评分的一致性**
- 验证：M4 起步前先用 20 条人工标注跑一次 Judge 准确度
- 不达标：调整 prompt 模板 / 改用多 judge 投票
