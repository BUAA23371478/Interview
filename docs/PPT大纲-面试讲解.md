## P4 · Agent 编排范式：为什么我不用 LangGraph / CrewAI

> ⭐ 这是最能体现思考深度的一页，务必讲透

- **视觉**：对比表

  | 框架 | 范式 | 我的结论 |
  |---|---|---|
  | LangGraph | 显式状态机、图编排 | 借鉴状态显式化与可回放思想，不引入依赖 |
  | CrewAI | 角色化 Agent + 任务委派 | 不适合：我的环节是**流水线**，不是协商 |
  | AutoGen | 对话式多 Agent 协作 | 不适合：token 成本与不确定性都更高 |
  | 自研编排 | 确定性流水线 + 条件分支 | ✅ 采用 |

- **核心论点**：编排框架不是越重越好。判断依据是 **Agent 之间是什么关系**：
  - 需要**协商/辩论/多轮讨价还价** → 对话式框架（AutoGen）有价值；
  - 需要**角色分工 + 动态委派** → CrewAI 有价值；
  - 我的场景是**固定环节 + 少量条件分支**，引入框架只会增加抽象层和不确定性。

  自研只要把三件事做好就够：**显式状态契约、可观测性、失败处理**。
  我把这三点做实了（`_new_state` 显式字段、`trace`/`difficulty_trace`、熔断+降级+幂等），
  比挂一个框架更能回答「你怎么保证它稳定」。

- **可能被追问**：
  - Q：「那你的编排和 LangGraph 的 checkpoint 有什么区别？」
    A：我用会话快照 + 版本号 CAS 做持久化，粒度是「一轮问答」；LangGraph 更细，支持节点级恢复。
    我的流程一轮只有几百毫秒的 LLM 时间，节点级恢复带来的复杂度不划算。
  - Q：「以后要加 Agent 怎么办？」
    A：新增一个 Agent 只需三步 —— 声明 `name`/`task`、实现 `run`、在 service 里编排。
    路由与熔断自动生效，因为调用点统一在 BaseAgent。

## P5 · Agent 清单与职责边界（附一个澄清）

- **视觉**：8 个环节的流水线图 + 每个环节标注「输入 / 输出 / 用哪个模型档位」
- **关键澄清**（主动讲，别等被问）：
  > 简历里写的「8 个 Agent」是**方法级能力的聚合说法**。
  > 特别澄清：**「追问」和「深挖」不是两个 Agent**，代码里只有 `interviewer.ask_followup` 一个方法，
  > 两种说法指向同一件事 —— 它们是**两次调用、不同触发条件**，不是两个职责重叠的 Agent。

  触发逻辑：
  ```
  should_followup = score.followup_needed and followup_count < max_followup(2)
  追问内容 ← score.key_missing（评分环节识别出的遗漏点）
  追问次数用尽 → 推进下一题（防同一话题死循环）
  ```
- **口播**：「主动澄清这一点，是因为如果我说有 8 个服务，第一个问题就会是『哪 8 个』，
  然后就会发现有两个是重复的 —— 那不如我自己先说清楚。」

- **可能被追问**：Q：「那为什么不真的拆成两个 Agent？」
  A：拆开会让追问变成一次额外的 LLM 往返（+1~2s），而追问的上下文（原题、回答、遗漏点）本来就在同一份 state 里，拆开只能靠复制传递。收益为负。

## P6 · 一次面试的完整时序（含并行化改造）

- **视觉**：时序图，标出并行段
  ```
  优化前（串行）： JD解析 ──▶ 简历匹配 ──▶ RAG检索 ──▶ 题目规划 ──▶ 出题
                  关键路径 = sum(全部)

  优化后（并行）： JD解析 ──▶ 简历匹配 ─┐
                                        ├─▶ 题目规划 ──▶ 出题
                  RAG检索 ─────────────┘
                  关键路径 = max(JD+简历, RAG)
  ```
- **要点**：RAG 检索只需要**原始 JD 文本**（本地 jieba TF-IDF 抽关键词，毫秒级），
  不依赖 JD 解析结果 → 原先「等解析完才能检索」是**人为的串行约束**，可以直接并行。
- **口播**：「这是典型的『关键路径优化』：先把依赖关系画出来，
  再问『这个依赖是真的必要，还是我写代码的顺序造成的』。」

## P7 · 难度自适应状态机：从装饰到真正生效

- **视觉**：左右对比 + 状态转移图
  ```
  优化前： update_difficulty() 把结果写进 state["current_difficulty"]
           interviewer 却读 plan[idx]["difficulty"]（预生成的）
           → 状态机只把结果渲染成 prompt 文本「当前难度：中等」
           → 自适应逻辑从未影响过任何一题

  优化后： effective_difficulty(state, plan_item) 是出题难度的唯一裁决者
           plan 只提供初始档位；每次转移写入 difficulty_trace（可回放可评测）
  ```
- **要点**：`difficulty_mode` 可切 `adaptive`（默认）/ `plan`（A/B 对照组）
- **口播**：「这个 bug 很典型：状态机看起来在工作（日志有输出、prompt 里有体现），
  但它写的字段和读的字段不是同一个。我是在画数据流图时才发现的。」
- **可能被追问**：Q：「怎么证明自适应有效？」
  A：`difficulty_trace` 记录了每次转移的 from/to/reason，可以直接画成难度曲线；
  配合 `plan` 模式可以做 A/B —— 这是下一步的评测计划。

## P9 · RAG 深挖①：为什么必须混合检索

- **视觉**：柱状图 + 表格（`bench/retrieval_eval_result.md`）

  | 方案 | Recall@5 | MRR@10 |
  |---|---|---|
  | 仅向量 | 39.3% | 0.2474 |
  | 仅 BM25 | 98.0% | 0.8642 |
  | 融合（修复后） | 97.1% | 0.8149 |

- **要点**：
  - 向量擅长「同义/语义相近」，BM25 擅长「术语精确命中」（如 `RRF`、`HNSW`、`RedLock`）；
  - 面试场景里技术名词密度极高，**必须有一路负责精确术语**；
  - 两者失败模式不同 → 互补性来自「不同错误模式」，不是「谁更强」。
- **⚠️ 诚实声明**（会被追问，主动说）：
  > 这张表的评测集是用文档小标题构造的查询，**天然偏向字面匹配**；
  > 且环境无 embedding Key，向量通道用哈希词袋替身。
  > 所以绝对数值不代表生产水平，**我只用它比较融合机制与权重是否合理**。
- **口播**：「我特意声明这个局限，因为如果我把 98% 说成『我的 RAG 效果很好』，
  懂行的面试官会立刻问评测集怎么标的 —— 那才是真正的失分点。」

## P10 · RAG 深挖②：融合失效 —— 一个静默 bug 的定位过程

> ⭐ 这一页是全场的「故事高潮」，讲成侦探片

- **视觉**：数据 + 两套 id 的对照

  | 方案 | Recall@5 | MRR@10 |
  |---|---|---|
  | 仅向量 | 39.3% | 0.2474 |
  | **融合（修复前）** | **39.4%** | **0.2517** |
  | 仅 BM25 | 98.0% | 0.8642 |

- **叙述线**：
  1. 我先跑了评测，发现融合结果**和「仅向量」几乎完全一样**（39.4% vs 39.3%，MRR 0.2517 vs 0.2474）；
  2. 这不正常 —— 融合至少应该比单路有变化。于是我去查两路结果的 id 格式：
     - 向量路：`1, 2, 3...`（DB 自增主键）
     - BM25 路：`doc:7#3`（`{doc_id}#{chunk_index}`）
  3. 两套命名空间**不相交** → 同一个 chunk 被两路同时召回时，RRF 里是两个不同的 key，得分**无法相加**；
  4. 结果：RRF 退化成「先列完全部向量结果、再接上 BM25 结果」的**并集**。
     BM25 独有的正确文档被挤到所有向量结果之后，超出 top_k 截断线 —— 融合形同虚设。
  5. 修复：统一 chunk id 为 `{doc_id}#{chunk_index}`。
- **结论数字**：**MRR 0.2517 → 0.8149，+223.8%**
- **口播金句**：
  > 「这个 bug 最危险的地方是**它不报错**。接口有返回、有分数、看起来正常，
  > 只有把两路结果的 id 打印出来对比才能发现。
  > 我因此给自己加了一条规则：**任何『融合/聚合』逻辑，第一件事是先验证 key 能不能对上。**」

- **可能被追问**：
  - Q：「怎么保证以后不再犯？」
    A：① 新增了 6 个融合回归用例，其中 `test_namespace_mismatch_degrades_fusion_to_union`
    专门断言「命名空间错位时 BM25 结果会被挤出截断线」；② chunk id 的生成收敛到一处。

## P11 · RAG 深挖③：融合算法与权重必须实测调参

- **视觉**：热力表格（`bench/retrieval_eval_result.md` 网格搜索）

  | 融合模式 | 权重(向量/BM25) | MRR@10 |
  |---|---|---|
  | RRF | 0.60 / 0.40（原默认） | **0.4035** ⚠️ |
  | RRF | 0.20 / 0.80 | 0.5923 |
  | score_norm | 0.60 / 0.40 | 0.7000+ |
  | **score_norm** | **0.35 / 0.65**（当前默认） | **0.8149** |
  | score_norm | 0.20 / 0.80（网格最优） | 0.8438 |
  | （参照）BM25 单路 | — | 0.8642 |

- **两个反直觉结论**：
  1. **固定权重 0.6/0.4 的 RRF 融合（MRR 0.4035）反而低于 BM25 单路（0.8642）**
     → 「接了两路 + RRF」**不等于**「更好」。弱通道会把强通道的正确结果挤出截断线。
  2. **融合算法比权重更关键**：同权重下 `score_norm` 0.8149 vs `rrf` 0.5644。
     - RRF 只用名次：第 1 名和第 20 名只差 `1/61 - 1/80`，弱通道的第 1 名能压过强通道的第 5 名；
     - `score_norm` 逐通道 min-max 归一化后加权求和，**保留了「这一路的置信度有多高」**。

- **工程落地**：
  - 新增 `score_norm` 融合，统一 `fuse()` 入口按 `RAG_FUSION_MODE` 分发，便于 A/B；
  - 默认改为 `score_norm` + 0.35/0.65；
  - 模式与权重全部可配，并在代码注释里写明「**换 embedding 模型或语料领域后必须重跑调参脚本**」。
- **口播**：「结论不是『我要用 score_norm』，而是『**融合参数必须有调参流程，不能拍脑袋写默认值**』。」

## P12 · RAG 深挖④：向量存储的三个技术细节

- **视觉**：三张卡片

  **① float32 vs float64**
  - 1024 维 float64 = 8KB/条；10 万条 ≈ 800MB
  - 改 float32：**内存减半到 390MB**，精度损失对余弦排序无实质影响
  - BLOB 加 4 字节魔数头（`F32/` `F64/`），自动兼容历史无头数据

  **② 字节序错配 —— 本次最隐蔽的坑**
  - `pack_vector` 用**大端** `struct.pack(">Nd")`（历史格式，必须兼容）
  - `np.frombuffer` **默认按本机小端**解析
  - 后果：整张索引矩阵变成 inf/NaN，**检索能跑、有结果、不报错，但排序完全错误**
  - 修复：显式声明 `>f4` / `>f8`，并加**装载后有限性校验**（发现非有限值即拒绝装载并告警）

  **③ 维度校验**
  - 原实现用 `min(len(a), len(b))` 静默截断比较
  - 256 维 mock 向量和 1024 维真实向量会「比较成功」但打分毫无意义
  - 改为**维度不一致直接抛错 + 告警**

- **口播金句**：
  > 「做性能优化最大的风险不是慢，是**变快的同时算错了**。
  > 这个字节序问题让我加了一条原则：**优化完必须做数值回环校验**（pack 完再 unpack，比对原值）。」

## P15 · 性能②：规模化曲线与 ANN 决策（数据推翻直觉）

- **视觉**：折线图 + 两张表

  **精确检索（numpy 批量余弦）**：`scale_result_exact.md`

  | chunk 数 | P50 | 索引内存 | 冷装载 |
  |---|---|---|---|
  | 5,000 | 0.6ms | 19.5MB | 108ms |
  | 20,000 | 2.6ms | 78.1MB | 480ms |
  | 50,000 | 6.0ms | 195.3MB | 1244ms |
  | 100,000 | **11.5ms** | 390.6MB | 2390ms |

  **HNSW ANN**：`scale_result_100k_hnsw.md`

  | chunk 数 | P50 | 冷启动（构建索引） |
  |---|---|---|
  | 100,000 | 1.4ms | **104.8 秒** ⚠️ |

- **两个决策**：
  1. **`RAG_ANN_THRESHOLD` 从 20000 上调到 200000**：
     10 万 chunk 精确检索只要 11.5ms，而 ANN 冷启动要重建 105 秒 —— 在 2 万规模切 ANN 是**过度设计**。
  2. **ANN 索引必须持久化**：文件名绑定 `dim / 规模 / max_id`，数据一变文件名就变，
     天然失效、不会读到脏索引。重建次数从「每次启动」降为「数据变更后一次」。

- **口播金句**：
  > 「我原本以为『数据量大了就该上 ANN』。实测数据告诉我两件事：
  > ANN 的**查询**确实快 8 倍，但它的**冷启动成本**是 105 秒 ——
  > 如果不做持久化，等于用『每次启动不可用 2 分钟』换『每次查询快 10ms』，完全不划算。
  > **技术选型要用数据验证，直觉经常是错的。**」

## P16 · 性能③：关键优化手法清单

- **视觉**：左右对照表

  | 环节 | 优化前 | 优化后 |
  |---|---|---|
  | 向量检索 | 每次 `select(Vector)` 拉全表 → 逐条 Python 余弦 | 内存 float32 矩阵 + numpy 批量余弦 / faiss HNSW |
  | 索引新鲜度 | 每次查询全表扫描 | DB 版本号 `(count, max_id)` 惰性重载 |
  | 向量存储 | float64（8KB/条） | float32（4KB/条）+ 4 字节格式头 |
  | BM25 构建 | pickle 语料 + **同步**全量重建（10 万规模阻塞事件循环 ≈64s） | DB 单一事实来源 + `asyncio.to_thread` + 版本失效通知 |
  | 双路召回 | 串行等待 | `asyncio.gather` 并行 |
  | 关键路径 | JD 解析 → 简历 → RAG → 规划（串行） | RAG 与「JD+简历」链并行 |
  | 维度过期 | `min(len)` 静默截断 | 显式校验 + 抛错告警 |

- **口播**：「注意最后一条 —— 它不是性能优化，是**正确性修复**。
  但它和性能优化写在同一个列表里，因为我的原则是：**性能改动必须同时保证正确性不退化**。」

## P17 · 网络与并发①：五层兜底体系

- **视觉**：金字塔图，从下到上

  ```
  第5层 并发一致性  会话写锁 + 快照乐观锁 CAS + 积分幂等键 + SSE 回放
  第4层 组件降级    Embedding冷却 / RAG失败不阻断 / 长期记忆失败只记日志 / SSE推送失败吞异常
  第3层 降级链      每任务 primary + fallbacks，逐档降级，全挂才抛错
  第2层 熔断        模型级三态熔断，直接跳过不可用档位
  第1层 超时重试    只重试可重试错误 + Full-jitter退避 + Retry-After 封顶
  ```

- **为什么是五层而不是一个 try/except**：
  每一层解决**不同时间尺度**的问题：
  - 重试 → 毫秒级抖动
  - 熔断 → 分钟级不可用
  - 降级链 → 单 provider 故障
  - 组件降级 → 非核心依赖故障
  - 并发一致性 → 数据正确性

- **口播**：「『兜底』不能是一句口号。我把它拆成五层，每层对应一个具体的时间尺度和故障类型，
  这样才知道自己覆盖了什么、还漏了什么。」

## P18 · 网络与并发②：熔断器三态机

- **视觉**：状态机图

  ```
  CLOSED ──连续失败≥3次──▶ OPEN ──冷却30s──▶ HALF_OPEN ──探测成功──▶ CLOSED
                            ▲                    │
                            └── 探测失败，冷却时间翻倍（上限300s）──┘
  ```

- **要点**：
  - `OPEN` 状态**直接跳过该模型**，不再浪费一次超时等待；
  - 按模型 id 隔离，单 provider 故障不误伤其他模型；
  - 半开只放行有限个探测请求；探测失败冷却翻倍，避免恢复期被持续打爆。
- **与降级链的关系（关键一句话）**：
  > **熔断决定「这一档还值不值得试」，降级链决定「不行就换谁」。**
- **效果量化**：
  - 没有熔断：单 provider 故障时，每个请求要等满 `60s 超时 × 3 次重试 ≈ 180s` 才轮到备用模型；
  - 有熔断：秒级切到备用模型，用户几乎无感。
- **可能被追问**：
  - Q：「阈值 3 次、冷却 30s 怎么定的？」
    A：按 DeepSeek 的限流特性 + 用户可接受等待时间定的，全部可配（`failure_threshold/cooldown/max_cooldown`），
    并且 `/health/metrics` 会暴露每个模型的熔断状态和剩余冷却时间，可以按真实数据再调。

## P19 · 网络与并发③：会话并发与一致性

- **视觉**：并发冲突场景图 + 解决前后对照

  **场景**：用户双击提交 / 网络超时后客户端自动重试 / 多标签页同时答题

  | 层 | 机制 | 解决什么 |
  |---|---|---|
  | 进程内 | 会话级 `asyncio.Lock`：已有请求在写时**快速失败**返回 409 | 避免两路 LLM 并行跑、白烧 token |
  | 跨进程 | 快照**乐观锁 CAS**：`expected_version` 与存储版本不一致即拒绝写入 → 409 | 多 worker/多副本下不静默覆盖 |
  | 客户端 | 409 语义明确 → 可安全重试；重试不会丢答题记录 | 幂等性 |
  | 计费 | `(request_id, kind)` 唯一约束 = 幂等键 | 重试不重复扣费 |
  | SSE | 环形缓冲 + `seq` + `Last-Event-ID` 回放 | 断线不丢进度、不重复推送 |

- **口播**：「这里我刻意选了『快速失败』而不是『排队等待』。
  因为这一步后面跟着 LLM 调用，让用户排在队尾等 5 秒，不如直接告诉他『正在处理中，请稍后重试』，
  客户端重试的成本几乎为零。」

## P20 · 统一模型网关：多模型 + 任务级路由

- **视觉**：路由表 + 架构图

  | 任务 | 模型档位 | 理由 |
  |---|---|---|
  | JD/简历解析、AI 预审 | cheap / standard | 结构化抽取，小模型够用 |
  | 出题、追问、评分 | standard | 需要中文表达质量 |
  | **复盘报告** | **strong（推理模型）** | 长链推理，报告质量敏感 |

- **为什么需要这层**：
  - 初版只有 `LLM_MODEL` + `LLM_BASE_URL` 两个全局配置 → 语义是「一个平台一个模型」；
  - 换模型要改环境变量重启；不同任务无法用不同模型；**价格无从计算**。
- **设计要点**：
  - 模型成为一等公民：`registry.py` 声明 provider / 接入点 / 调用风格 / 上下文 / 计价 / 能力标签；
  - 5 个模型（deepseek-chat / reasoner / v4-flash / qwen-plus / qwen-turbo）；
  - 用户可通过 `X-LLM-Model` 头覆盖；**填了非法模型名会被忽略并回落策略**，
    不会因为用户填错就让整场面试不可用；
  - **接入点收敛**：所有 Agent 走 `BaseAgent.invoke_llm*`，路由 + 降级 + 熔断只接一次。
- **成本论点**：把贵模型精准投到推理密集环节，其余走性价比模型 —— 这是可量化的成本优化。
- **踩坑记录（讲出来显得真实）**：
  > 一开始我把「用户偏好模型」和「实际生效模型」放在同一个 contextvar 里，
  > 结果路由写入的实际模型被下一轮当成了用户偏好 —— 一次请求里所有任务都退化成同一个模型，
  > 任务级路由完全失效。后来拆成两个 contextvar 才解决。

## P21 · 积分计费：预扣 + 结算 + 幂等

- **视觉**：时序图 + 流水表

  ```
  请求进入
    ├─ pre_deduct  按任务预估冻结积分 ──余额不足──▶ 直接拒绝（不产生任何 LLM 成本）
    ├─ 执行 LLM 调用（真实 usage 回填 Meter）
    └─ settle      按真实成本结算（多退少补）
                   请求失败无产出 → release 全额退回
  ```

- **为什么必须预扣（面试高频追问点）**：
  > 事后扣在并发下会被套利：用户余额 10 积分，同时发起 5 个各消耗 10 积分的请求，
  > 5 个都先跑完 LLM 再扣费，余额被扣成负数 —— 而成本已经真实发生，追不回来。

- **幂等**：`(request_id, kind)` 唯一约束即幂等键。客户端重试/网关重放 → 第二次插入冲突 → 识别为已处理。
- **汇率**：1 元 = 1000 积分；成本由**真实 usage × 模型单价**折算
  → 「积分消耗」与「token 账单」是一条可对齐的线，不是拍脑袋的固定值。
- **充值（占位）**：只实现「入账」一端，幂等键显式暴露为 `order_id`。
  接入支付后把渠道回调的订单号原样传入，即获得「回调重放不重复入账」的保证。
  API 默认返回 503，明确「未接入真实支付」。
- **口播**：「充值我**故意没做完**。因为接入真实支付涉及验签、对账、退款，
  做一半比不做更危险。我把入账端和幂等键设计好，接口留着 —— 这是负责任的做法。」
