## 0. 一句话结论

在**不改业务语义**的前提下，把项目从「demo 合格」改造成「扛得住面试三层追问」：

- 检索层：2 万 chunk 单次检索 **4914ms → 1.2ms（≈4095×）**，10 万 chunk 仅 11.5ms，且内存可控（390MB）；
- 检索质量：修复融合失效后 MRR **0.2517 → 0.8149（+223.8%）**；
- 可靠性：修掉 7 个会导致「静默错误」的 P0 缺陷，并补上熔断 / 降级链 / 幂等 / 乐观锁；
- 工程化：新增统一模型网关（多模型 + 任务路由 + 降级链）与积分计费（预扣/结算/幂等）；
- 测试：**6 → 43 个用例全绿**，新增用例均为「旧实现会失败、新实现通过」的回归护栏。

## 1. 优化前的诊断（用代码与数据说话，不靠感觉）

### 1.1 性能基线（`bench/scale_result_before.md`）

用真实 `VectorStore.search` 代码路径、1024 维向量、独立子进程隔离测量：

| chunk 数 | P50 | P95 | 说明 |
|---|---|---|---|
| 500 | 94.1ms | 101.0ms | 已明显超出一个交互式检索的合理预算 |
| 5,000 | 1060.1ms | 1126.5ms | 秒级，用户可感知卡顿 |
| 20,000 | 4914.3ms | 5049.4ms | 接近 5 秒，用户体验已不可接受 |

线性外推 10 万 chunk ≈ **35 秒**。而「知识库从不到 100 篇扩到 1 万+」是明确的产品规划 —— 差距约 5 个数量级。

### 1.2 七个 P0 缺陷（均有代码证据）

| # | 缺陷 | 后果 | 位置 |
|---|---|---|---|
| 1 | **BYOK 密钥串号**：`_client` / `_current_key` 单槽缓存，多用户并发互相覆盖 | 用户 A 的请求可能用用户 B 的 key 计费 | `app/llm.py` |
| 2 | **难度状态机空转**：状态机只把结果写进 prompt 文本，出题取的是预生成的 `plan[idx].difficulty` | 「连对升级/连错降级」从未影响过题目难度，自适应是装饰 | `app/agents/difficulty_fsm.py`、`interviewer.py` |
| 3 | **O(N) 全表扫描**：每次检索 `select(Vector)` 拉全表 → 逐条 Python 余弦 | 2 万 chunk 4.9s，10 万 chunk 不可用 | `app/rag/vector_store.py` |
| 4 | **Embedding 永久降级**：API 失败一次就置 `_api_failed=True` 且永不复位 | 进程内所有向量静默退化为 mock，检索质量无声崩塌 | `app/embedding.py` |
| 5 | **SSE 静默丢事件**：两阶段连接模式下，无连接时 `emit()` 直接 `return False` | 前端慢挂连接就丢首题，且后端无任何异常日志 | `app/sse/emitter.py` |
| 6 | **会话无并发控制**：读-改-写无锁、无版本校验 | 双击/网络重试导致答题记录丢失、题目跳变 | `app/services/interview_service.py` |
| 7 | **双源漂移 + 命名空间错位**：BM25 走 pickle 语料、向量走出自增主键，两路 id 不相交 | 看起来「接了双路检索」，实际 RRF 无法融合（详见 §3） | `app/rag/bm25.py`、`vector_store.py`、`hybrid.py` |

### 1.3 一个必须先澄清的架构事实

**「追问」和「深挖」不是两个 Agent。**

代码里只有 `interviewer.ask_followup` 一个方法（`app/agents/interviewer.py`），
两种说法指向的都是它，共用同一套 `FOLLOWUP_PROMPT`。
它们是**两次调用、不同触发条件**，而不是两个职责重叠的 Agent：

- 触发条件：`score.followup_needed == True` 且 `followup_count < max_followup(2)`；
- 追问内容由 `key_missing`（评分环节识别出的遗漏点）驱动，属于「同一主题的收敛式深挖」；
- 追问次数用尽即推进到下一题，避免陷入同一话题死循环。

原简历写「8 个 Agent」是**方法级能力的聚合说法**，不能对应 8 个独立服务的 Agent。
面试时应主动说明这一点，否则被追问「哪 8 个」会很被动。

## 3. 检索层：性能与质量

### 3.1 性能（`bench/scale_result_after.md` 等）

| chunk 数 | 优化前 P50 | 优化后 P50 | 加速比 |
|---|---|---|---|
| 500 | 94.1ms | 0.2ms | **470×** |
| 5,000 | 1060.1ms | 0.7ms | **1514×** |
| 20,000 | 4914.3ms | 1.2ms | **4095×** |

精确检索（numpy 批量余弦）的规模化曲线（`bench/scale_result_exact.md`）：

| chunk 数 | P50 | 索引内存 | 冷装载 |
|---|---|---|---|
| 5,000 | 0.6ms | 19.5MB | 108ms |
| 20,000 | 2.6ms | 78.1MB | 480ms |
| 50,000 | 6.0ms | 195.3MB | 1244ms |
| 100,000 | 11.5ms | 390.6MB | 2390ms |

**结论：numpy 精确检索在 10 万 chunk（≈1 万篇文档 × 10 块）量级依然只需 11.5ms，
完全满足交互式响应预算。** 因此 `RAG_ANN_THRESHOLD` 依实测从 20000 上调到 200000 —— 
在 2 万规模就切 HNSW 是过度设计（见下）。

### 3.2 ANN 索引：一个被数据推翻的直觉

`bench/scale_result_100k_hnsw.md`：

| chunk 数 | P50 | 冷启动（构建索引） |
|---|---|---|
| 100,000 | 1.4ms | **104.8 秒** |

HNSW 把查询从 11.5ms 降到 1.4ms，但**冷启动要重建 105 秒**。
如果每次进程启动都重建，服务启动即不可用。

修复：**索引持久化**（`vector_store._build_or_load_ann`），文件名绑定
`dim / 规模 / max_id`，数据一变文件名就变 → 天然失效，不会读到脏索引。
重建次数从「每次启动」降为「数据变更后一次」。

### 3.3 检索质量：修复「假融合」

评测方法（`bench/retrieval_eval.py`）：known-item retrieval，49 篇种子文档、
591 条去歧义查询（取自文档小标题），在**文档级**计算 Recall@5 / MRR@10 / nDCG@10。

| 方案 | Recall@5 | MRR@10 | nDCG@10 |
|---|---|---|---|
| 仅向量通道 | 39.3% | 0.2474 | 0.3209 |
| 仅 BM25 通道 | 98.0% | 0.8642 | 0.8971 |
| **融合（修复前：命名空间错位）** | **39.4%** | **0.2517** | 0.3316 |
| 融合（修复后 + 调参，当前默认） | 97.1% | **0.8149** | 0.8595 |

**关键证据**：修复前的融合结果与「仅向量单路」几乎完全重合（39.4% vs 39.3%），
说明 **BM25 那一路的结果根本没参与排序**。原因是：

- 向量路结果 id 用 DB 自增主键（`1, 2, 3...`）；
- BM25 路结果 id 用 `{doc_id}#{chunk_index}`（`doc:7#3`）。

两套命名空间不相交 → 同一个 chunk 被两路同时召回时得分无法相加 →
RRF 退化为「先列完全部向量结果、再接上 BM25 结果」的并集。
BM25 独有的正确文档被挤到所有向量结果之后，超出 `top_k` 截断线。

修复：统一 chunk id 为 `{doc_id}#{chunk_index}`，RRF 才真正生效。
**MRR 0.2517 → 0.8149，+223.8%。**

### 3.4 融合算法与权重：调参不是可选项

网格搜索（同上评测集）发现两个反直觉结论：

1. **固定权重 0.6/0.4 的 RRF 融合（MRR 0.4035）反而低于 BM25 单路（0.8642）** ——
   弱通道把强通道的正确结果挤出了截断线。「接了两路 + RRF」不等于「更好」。
2. **融合算法比权重更关键**：同权重下 `score_norm` MRR 0.8149 vs `rrf` 0.5644。

因此：
- 新增 `score_norm` 融合（逐通道 min-max 归一化后加权求和），保留「这一路置信度有多高」的信息；
- 默认改为 `score_norm` + 权重 0.35/0.65；
- 融合模式与权重全部做成配置项，并在注释中明确「换 embedding 模型或语料领域后必须重跑调参脚本」。

> ⚠️ 方法论声明（避免误读）：评测环境无 embedding API Key，向量通道用「哈希词袋向量」
> 替代 bge-m3；查询由小标题构造，天然偏向字面匹配。
> **因此上表的绝对数值不代表生产水平，只用于比较融合机制与权重是否合理。**

## 4. 统一模型网关（M2）

### 4.1 问题

初版只有 `LLM_MODEL` / `LLM_BASE_URL` 两个全局配置，语义是「一个平台一个模型」：
换模型要改环境变量重启，不同任务无法用不同模型，价格也无从计算。

### 4.2 设计

```
app/gateway/
  registry.py   模型注册表：id / provider / base_url / api_style / 上下文 / 计价 / 能力标签
  router.py     任务 → 模型档位策略 + 降级链（TASK_POLICY）
  breaker.py    模型级三态熔断器
  credits.py    积分：预扣 / 结算 / 退回 / 充值（占位）
```

**任务级路由**（不是全局一个模型）：

| 任务 | 档位 | 理由 |
|---|---|---|
| JD/简历解析、AI 预审 | cheap / standard | 结构化抽取，小模型够用 |
| 出题、追问 | standard | 需要中文表达质量 |
| 评分 | standard | 窄任务，要求稳定 |
| **复盘报告** | **strong（推理模型）** | 长链推理，报告质量敏感 |

把贵模型精准投到推理密集环节，其余走性价比模型 —— 这是可量化的成本优化。

**接入点收敛**：全部 8 个 Agent 的 LLM 调用都走 `BaseAgent.invoke_llm*`，
因此任务路由 + 降级链 + 熔断只在**一处**接入（`base_agent._call`），
不散落到各 Agent 里。

**请求级模型隔离**：用两个独立 contextvar 分别承载「用户偏好模型」与「实际生效模型」。
若共用一个，路由写入的实际模型会被下一轮当成用户偏好，
导致一次请求里所有任务退化成同一个模型（任务级路由失效）—— 这是实现时踩到的坑。

### 4.3 积分计费

**为什么是「预扣 + 结算」而不是「事后扣」**：
事后扣在并发下会被套利 —— 用户余额 10 积分，同时发起 5 个各消耗 10 积分的请求，
5 个都先跑完 LLM 再扣费，余额被扣成负数，而成本已真实发生且无法追回。

流程：

1. `pre_deduct`：按任务预估冻结积分。**余额不足直接拒绝，不产生任何 LLM 成本**；
2. `settle`：真实 usage 出来后按「多退少补」调整；
3. `release`：请求整体失败（无有效产出）时全额退回。

**幂等**：`(request_id, kind)` 唯一约束就是幂等键。客户端超时重试、网关重放，
第二次写入直接冲突并被识别为「已处理」，不会重复扣费。

**汇率与对齐**：1 元 = 1000 积分；成本由真实 usage × 模型单价折算，
所以「积分消耗」与「token 账单」是一条可对齐的线，不是拍脑袋的固定值。

**充值**：只实现「入账」一端，并把幂等键显式暴露为 `order_id`。
接入真实支付渠道后，把回调里的订单号原样传入即可获得「回调重放不重复入账」的保证。
API 默认返回 503（`CREDIT_RECHARGE_ENABLED=false`），明确「未接入真实支付」。

### 4.4 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/billing/models` | 模型目录（计价、档位、能力标签） |
| GET | `/billing/routing` | 任务→模型路由表（解释「为什么这个环节用这个模型」） |
| GET | `/billing/balance` | 积分余额 |
| GET | `/billing/ledger` | 积分流水 |
| POST | `/billing/recharge` | 充值（占位） |
| GET | `/health/metrics` | 检索层/熔断器/模型/SSE 运行时可观测指标 |

用户也可通过 `X-LLM-Model` 请求头指定偏好模型；填了注册表里没有的名字会被**忽略并回落任务策略**，而不是让整场面试不可用。

## 5. 网络、并发与兜底（M3）

用户明确要求「出错误了怎么处理，兜底机制一定要讲清楚」。整体是**五层**：

### 第 1 层：超时与重试（`app/llm.py`）

- 单一超时 `LLM_TIMEOUT`（默认 60s），SDK 自身重试关闭（`max_retries=0`），重试由本模块统一控制；
- **只重试值得重试的错误**：408 / 409 / 425 / 429 / 5xx 与网络类异常；
  401 / 403 / 404 / 400 立即失败（重试没有意义，只会浪费用户时间）；
- **Full-jitter 退避 + 封顶 6s**：交互式场景下，60s 的重试等价于停机；
- 若响应带 `Retry-After`，优先遵循但同样封顶。

### 第 2 层：模型级熔断（`app/gateway/breaker.py`）

重试解决「偶发抖动」，熔断解决「持续不可用」。

```
CLOSED ──连续失败≥3──▶ OPEN ──冷却30s──▶ HALF_OPEN ──成功──▶ CLOSED
                        ▲                    │
                        └──── 探测失败，冷却翻倍 ────┘
```

- `OPEN` 状态**直接跳过该模型**，不再浪费一次超时等待；
- 按模型隔离，单 provider 故障不误伤其他模型；
- 半开探测失败冷却时间翻倍（上限 300s），避免恢复期被持续打爆。

**效果**：单 provider 故障时，用户感知从「等满超时（60s×3≈180s）」变为「直接换模型（毫秒级）」。

### 第 3 层：降级链（`app/gateway/router.py`）

每个任务配置 `primary + fallbacks`，逐档降级，全挂才抛错。
**熔断决定「这一档还值不值得试」，降级链决定「不行换谁」**，两者叠加。

### 第 4 层：组件级降级

| 组件 | 故障 | 降级行为 |
|---|---|---|
| Embedding API | 失败 | 进入 60s 冷却（不是永久降级），冷却期内走纯关键词检索，冷却后自动恢复 |
| RAG 检索 | 抛错 | 记 warning，`rag_context=""`，出题退化为「无参考资料」，**不阻断面试** |
| 长期记忆 | 读写失败 | try/except 包裹，只记日志，不影响主流程 |
| SSE | 推送失败 | 吞掉异常只记 debug，不影响业务返回 |

### 第 5 层：并发与一致性

| 场景 | 机制 |
|---|---|
| 同一会话并发提交 | 进程内会话级写锁：已有请求在写时**快速失败**返回 409，避免两路 LLM 白烧 token |
| 跨进程/多副本并发 | 快照乐观锁（`(request_id, kind)` 版本号 CAS）：版本失配拒绝写入并返回 409，绝不静默覆盖 |
| 客户端重试 | 409 语义明确，客户端可安全重试；重试不会丢答题记录 |
| 计费重放 | 积分幂等键 + 唯一约束 |
| SSE 断线 | 环形缓冲 + `seq` + `Last-Event-ID` 回放，不丢进度、不重复推送 |
| 会话通道泄漏 | 通道空闲回收（`sweep`） |

## 6. 可观测性（回答「你怎么知道哪个环节慢、哪一步烧钱」）

新增 `app/observability.py`：

- `Meter` 挂在 contextvar 上，按请求隔离，多租户并发不互相污染；
- LLM 客户端把 API 返回的 **真实 usage** 回填进当前 Meter（不是估算）；
  流式调用通过 `stream_options={"include_usage": True}` 拿末帧 usage，
  服务端不支持时自动降级；
- `span()` 包裹每个 Agent 调用，记录 耗时 / token / 成本 / 状态，落到 `state["trace"]`；
- `trace` 随接口响应返回，前端可直接展示「这一步花了多久、烧了多少 token」。

`/health/metrics` 暴露：向量索引规模/内存/上次查询延迟、BM25 语料与构建耗时、
embedding 缓存命中率与冷却状态、LLM key 池规模、各模型熔断状态、活跃 SSE 通道数。

### 优化过程中新发现并修复的 3 个隐蔽缺陷

1. **向量 BLOB 字节序错配**（严重）：`pack_vector` 用大端 `struct.pack(">Nd")`，
   而 `np.frombuffer` 默认按本机小端解析 → 整张索引矩阵变成 inf/NaN。
   症状是「检索能跑、有结果，但排序完全错误」，**不会报错**。
   已改为显式 `>f4` / `>f8` 并加装载后有限性校验（发现非有限值即拒绝装载并告警）。
   这是本次优化中最值得讲的坑：性能优化的前提是正确性，否则只是「更快地算错」。

2. **HNSW 冷启动 105s**：见 §3.2，已通过索引持久化解决。

3. **RRF 权重未调参导致融合反而更差**：见 §3.4。

## 8. GitHub 高质量项目调研与选型论证

| 项目 | 核心范式 | 是否采用 | 理由 |
|---|---|---|---|
| **LangGraph** | 显式状态机 / 图编排，状态在节点间显式传递，支持检查点与中断恢复 | 部分借鉴 | 其「显式状态 + 可回放」思想已吸收进本项目（`difficulty_trace`、`trace`、会话快照）；但本项目流程固定为线性 + 条件分支，引入 LangGraph 会带来额外抽象层与依赖，收益不足 |
| **CrewAI** | 角色化 Agent + 任务委派 | 不采用 | 面向「多角色协商」场景；本项目 8 个环节是**流水线**关系而非协商关系，强行角色化只会增加 LLM 调用次数与不确定性 |
| **AutoGen / Microsoft Agent Framework** | 对话式多 Agent 协作 | 不采用 | 同理，且对话式编排的 token 成本与不可控性对面试场景不利 |
| **OpenAI Swarm / Agents SDK** | 轻量 handoff | 不采用 | handoff 模型与本项目的确定性流程不匹配 |

**选型结论（也是面试时的加分点）**：
编排框架不是越重越好。本项目的 Agent 关系是**确定性流水线 + 条件分支**，
自研编排只要把三件事做好就够：**显式状态契约、可观测性、失败处理**。
我们把这三点做实（`_new_state` 显式字段、`trace`/`difficulty_trace`、熔断+降级+幂等），
比引入一个框架更能回答「你怎么保证它稳定」。

同时吸收了业界成熟实践：RRF 混合检索、HNSW ANN、Cross-Encoder 重排（预留）、
任务级模型路由（Router 模式）、预扣式计费（预授权模式）。
