# AI 面试智能体 · 深度优化规划 v1

> 目标：把项目从「demo 合格」提升到「能扛住面试官三层追问」的水平。
> 核心叙事：**可测量的质量（评测集）→ 可验证的优化（对比数据）→ 可讲透的工程细节（并发/性能/成本/编排范式）**

---

## 一、现状诊断

代码实际水平高于简历描述（已有 BYOK contextvar、RRF 混合检索、SSE、平台化适配、审核链路），
但存在一批「一追问就见底」的问题。以下按严重度分级，均标注代码证据。

### P0 — 正确性 / 并发缺陷（面试官必问，现在会穿帮）

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| 1 | **BYOK 多租户串号**：客户端单例缓存 `self._client/_current_key`，并发请求下 A 用户请求可能复用 B 用户的 client/key | `app/llm.py:202-214` | 跨用户 key 泄漏，多租户隔离承诺失效 |
| 2 | **向量检索全表扫描**：`select(Vector)` 全量加载 + Python 逐条算余弦，无 ANN 索引、无分页 | `app/rag/vector_store.py:45-78` | O(N) 复杂度；万级 chunk 每查一次拉全表（~80MB） |
| 3 | **Embedding 失败永久降级 + 维度静默截断**：`_api_failed=True` 不可恢复；mock 256 维与 bge-m3 1024 维混库，`cosine_similarity` 用 `min(len)` 静默比较 | `app/embedding.py:62-65,107-112` | 质量静默崩塌，检索结果无声变垃圾 |
| 4 | **难度自适应是假的**：FSM 更新 `current_difficulty`，但出题取 `question_plan[idx].difficulty`（plan 一次性预生成），FSM 值只进 prompt 文本 | `app/agents/difficulty_fsm.py` + `app/agents/interviewer.py:74-96` | 简历写的「连对升级/连错降级」实际未生效 |
| 5 | **SSE 两阶段连接竞态**：无连接时 `emit` 静默返回 False 丢事件；`SSEManager._connections` 为进程内 dict；无 `Last-Event-ID` 重放 | `app/sse/emitter.py:71-76,24-31` | 前端慢挂连接就丢首题；多 worker/多副本直接断流 |
| 6 | **会话快照无并发控制**：Redis 全量 `load → 改 → save`，无 CAS/乐观锁 | `app/services/interview_service.py:298-309` | 并发提交（双击/重放）导致丢更新 |
| 7 | **双检索源不一致**：BM25 语料 pickle 与向量表各自维护，删除/审核文档后 pickle 不更新；进程内单例多副本内存不一致 | `app/rag/bm25.py:34-48` | 召回结果与主数据漂移；已删文档仍被召回 |

### P1 — 工程深度不足（这是「浅显」的真正来源）

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| 8 | **编排是手写串行 if/else**，非真正编排：无 Graph/DAG、无节点契约、无并行 fan-out | `app/services/interview_service.py:63-87` | JD→简历→RAG→规划 全串行，首题延迟白白翻倍 |
| 9 | **零可观测性**：无 trace_id / span / 每步耗时 / token 计量 | 全局 | 面试问「你怎么知道哪慢」无法回答 |
| 10 | **无评测集与指标**：仅 3 个功能单测，没有检索质量与端到端指标 | `backend/tests/` | 所有优化无法证明收益，PPT 无数据 |
| 11 | **无多模型路由与计量**：base_url/model 硬编码走 env，`User.credits` 字段存在但无实现 | `app/llm.py:74-84` + `app/models.py:30` | 需求 1 的落地空间 |
| 12 | **韧性不足**：重试无 jitter、无熔断/限流/幂等键；`_safe_truncate` 硬截断无 token 预算管理 | `app/llm.py:245-270` | 长会话上下文溢出、风暴重试 |

## 二、优化目标与验收标准

| 维度 | 现状 | 目标 | 验收方式 |
|------|------|------|----------|
| 检索质量 | 无指标 | Recall@5 / MRR@10 / nDCG@10 有基线且可提升 | `make bench-retrieval` 出报告 |
| 检索性能 | O(N) 全表扫描 | P95 检索延迟下降 ≥10x（千级 chunk） | benchmark 对比曲线 |
| 首题延迟 | 全串行 | 下降 ≥40%（并行化 JD∥简历∥RAG） | 端到端 benchmark |
| 多租户 | key 可串号 | 并发 100 请求 0 串号 | 新增并发隔离测试 |
| 自适应 | 未生效 | FSM 真正驱动出题难度，有 A/B 曲线 | 会话回放对比 |
| 成本 | 不可见 | 每会话 token/积分可计量、可对账 | 积分流水与 usage 一致 |
| 可观测 | 无 | 每步 span（耗时/token/成本）落库可查 | trace 页面/日志 |

## 三、方向 0：评测基建（**必须最先做**）

没有它，后面所有优化都无法证明收益，PPT 也只能讲「我觉得变快了」。

### 0.1 三层测试集

| 层级 | 规模 | 构造方式 | 指标 |
|------|------|----------|------|
| L1 检索集 | 200-300 条 query→gold chunk | 用现有 300+ 题库反向生成（题目当 query，出处 chunk 当 gold）；标注 3 档相关性 | Recall@5、MRR@10、nDCG@10、含/不含 rerank 对比 |
| L2 评估器可信度集 | 100 条「答案-人工分」对 | 人工标注 + 交叉复核 | 与人工分的 Spearman / QWK、四维一致性 |
| L3 端到端会话集 | 20-30 个脚本化会话 | 固定 JD+简历+预设答案序列（含对/错/模糊三类） | 首题延迟、每轮 P95、追问触发准确率、难度曲线合理性 |

### 0.2 基准工具

```
backend/bench/
├── datasets/          # L1/L2/L3 数据集（JSONL，可版本化）
├── run_retrieval.py   # 检索指标
├── run_evaluator.py   # 评估器一致性
├── run_e2e.py         # 端到端延迟/行为
└── report.py          # 生成 Markdown + JSON 报告
```

统一入口：`make bench` → 产出 `bench/reports/{ts}.md` + `.json`（含基线快照，支持 diff）。

### 0.3 可视化产物

- 优化前 vs 后对比柱状图 / 折线图（检索指标、延迟分位、成本）
- 难度自适应曲线（连对/连错下的难度轨迹，证明 FSM 生效）
- 每轮 token / 积分消耗堆叠图

## 四、方向 1：统一 API 网关 + 多模型 + 积分

### 4.1 分层设计

```
业务层（Agents）
      ↓ 统一接口：await gateway.chat(task=TaskType.QUESTION_GEN, ...)
路由层  ModelRouter  ── 策略：任务类型映射 / 成本优先 / 质量优先 / 降级链
适配层  ProviderAdapter ── DeepSeek / SiliconFlow / OpenAI / 通义 / (可选)本地 vLLM
计量层  MeteringHook ── 从 usage 字段取 token → 按单价表折算 credits
账户层  CreditService ── 预扣 → 结算 → 流水记账 → 对账
```

### 4.2 关键设计点（面试可讲）

1. **模型注册表**（配置化，热更新）：
   `id / provider / base_url / model_name / context_window / price_in / price_out / capability_tags`
2. **按任务路由**：出题/追问走强模型，点评/收尾走便宜模型 → 成本可降 40%+，且可 A/B 验证质量损失
3. **降级链**：`主模型 → 备模型 → 缓存/模板兜底`，配熔断器（连续失败 N 次断路，半开探测）
4. **BYOK 与平台额度并存**：`用户 key → 不扣积分` / `平台 key → 扣积分`（清晰的多租户计费边界）
5. **计量**：优先用 API 返回的 `usage`（准确）；无 usage 时用 tiktoken 估算；流式需末帧聚合
6. **预扣-结算两阶段**（防超支的关键）：
   - 请求前按 `估算输入 token + max_tokens` 预扣
   - 完成后按实际 usage 结算，差额退回
   - 余额不足直接 402，避免「跑完了才发现扣不动」
7. **幂等**：`X-Request-Id` + 唯一索引，重试/重放不重复扣费
8. **并发安全**：Redis 原子扣减（Lua 脚本）为主，DB 流水为审计账本；定时对账兜底
9. **充值占位**：只建 `credit_orders` 表 + `POST /credits/recharge` 返回「未开放」的 stub，回调端点预留签名校验骨架

### 4.3 数据表（新增）

- `credit_accounts(maoo_user_id, balance, frozen, version)` — 余额 + 乐观锁版本
- `credit_transactions(id, user_id, request_id UNIQUE, type, amount, model, tokens_in/out, balance_after, created_at)` — 不可变流水账
- `model_pricing(model_id, price_in, price_out, updated_at)`
- `credit_orders(...)` — 充值占位

### 4.4 接口

```
GET  /gateway/models            # 可选模型列表（含价格、能力标签）
POST /gateway/chat              # 统一对话（透传 → 计量 → 扣费）
GET  /credits/balance
GET  /credits/transactions      # 分页流水
POST /credits/recharge          # 占位
```

### 4.5 前端

模型选择器（对话页 + 个人中心）、余额卡片、流水明细表、用量趋势图。

## 五、方向 2：Agent 编排架构升级

### 5.1 从「手写串行」到「显式 Graph 编排」

```
                ┌─────────────── Orchestrator（tracer + 状态机 + 预算）───────────────┐
                │                                                                    │
 Start ──┬──▶ JDAnalyzer ──┐                                                          │
         ├──▶ ResumeAnalyzer ──┼──▶ RAGRetrieve ──▶ QuestionPlanner ──▶ [State: ASKING] │
         └──▶ (并行 fan-out)  ┘                                    │                   │
                                                                  ▼                   │
        [State: EVALUATING] ◀── Answer ── AskQuestion ◀──┐   Evaluator               │
                │                                        │        │                  │
                ├── score < 阈值 且 追问数 < 上限 ──▶ [State: FOLLOWUP] ──┘            │
                ├── 全题完成 ──▶ [State: WRAPPING] ──▶ Report + StudyPlan ──▶ END     │
                └── 达到轮次上限 ─────────────────────────────────────────────────────┘
```

**要点：**
1. **节点契约化**：每个 Agent 定义 `Input/Output` Pydantic schema，可单测、可 mock、可替换
2. **真状态机**：把 `difficulty_fsm` 从「难度升降函数」升级为完整会话 FSM
   （`IDLE/ASKING/EVALUATING/FOLLOWUP/WRAPPING/DONE`），难度作为**决策函数**注入出题节点
   → **修复方向 0 诊断中的 P0-4，让自适应真正生效**
3. **并行 fan-out**：启动阶段 JD 解析 ∥ 简历解析 ∥ RAG 预检索 三路并发（`asyncio.gather`），首题延迟显著下降
4. **上下文工程**：token 预算管理器（按节点分配预算 + 超限摘要压缩），替换裸 `_safe_truncate`
5. **可观测性**：`Trace` 上下文（trace_id → span：node/latency/tokens/cost/status），落库 + 提供查询接口

### 5.2 BYOK 隔离修复（P0-1）

- 方案 A（推荐）：**按 key 建 client 池**（LRU + TTL），key 从 contextvar 取，client 不再「谁最后用谁」
- 方案 B：每请求 `async with` 临时 client（简单但连接复用差）
- 加并发隔离测试：100 并发不同 key → 断言每次实际使用的 key 与请求头一致

### 5.3 SSE 可靠性（P0-5）

- 事件带**单调递增 seq**，前端重连带 `Last-Event-ID`，服务端从 Redis Stream 重放缺失事件
- 连接未就绪时**事件入 Redis 缓冲**而非静默丢弃；连接建立后回放
- 队列状态外置（Redis）+ 心跳与超时清理；单实例内存模式保留为降级路径

### 5.4 会话状态并发安全（P0-6）

- 快照加 `version` 字段，写回用 CAS（Lua `WATCH/MULTI` 或 `SETNX` 锁）
- 关键写操作幂等：`(session_id, question_idx, answer_hash)` 唯一约束

### 5.5 检索层重构（P0-2/3/7）

| 项 | 方案 |
|----|------|
| ANN 索引 | 千级以内：`faiss-cpu` / `sqlite-vec` 内嵌（零运维）；万级以上：Qdrant/Milvus（Docker 起，面试可讲） |
| 存储 | float32 存储、批量矩阵检索（numpy 向量化替代 Python for 循环） |
| Embedding | 失败仅降级**当前请求**（不置永久标记）；维度不符**显式报错**而非静默截断；query embedding 加 LRU 缓存 |
| 一致性 | BM25 语料改为**从 DB 构建 + 版本号/更新时间戳**，索引重建走统一入口；删除文档同步失效 |
| 融合 | 补 Cross-Encoder（bge-reranker）精排作为可选项，与 LLM 精排做成本/质量对比 |
| 中文分块 | 改为**标题层级感知**（Markdown 按 `#` 结构切分 + 父块上下文），对比固定长度分块的检索指标提升 |

```

7  检索性能优化：全表扫描 → ANN（延迟对比图）
8  多租户与 BYOK：contextvars 隔离 + 踩坑（串号 bug 复盘）
9  统一网关与多模型路由 + 积分计量（架构图 + 成本对比）

```

### 6.2 追问 QA 手册（30 问）

按主题分组，每题给出「一句话结论 + 展开 3 层」：
- RAG：为什么 RRF 而不是加权求和？k=60 怎么定？分块大小怎么选？rerank 收益与成本？
- 性能：延迟瓶颈在哪？怎么测的？P95 与均值差异原因？
- 网络：LLM 超时/限流/抖动怎么处理？重试风暴怎么防？
- 并发：contextvars 原理？为什么单例 client 会串号？Redis 与 DB 一致性？
- 成本：token 怎么算？流式 usage 怎么拿？预扣额度怎么估？
- 评估：LLM-as-judge 可靠吗？怎么校准？人工一致性多少？

### 6.3 简历改写建议

现有描述偏「功能罗列」，建议改为**「问题 → 方案 → 数据」**句式，例如：
> 「检索层原为全表扫描 + 逐条余弦（O(N)），重构为向量化批量检索 + ANN 索引，
> 千级语料下 P95 延迟从 XXXms 降至 XXms；建立 300 条检索评测集，
> Recall@5 从 X.XX 提升至 X.XX。」

## 九、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Embedding/Rerank 依赖外部 API，网络抖动污染 benchmark | 数据不可信 | benchmark 支持缓存回放（record/replay），固定随机种子 |
| LLM 输出非确定性，评估器指标波动 | 结论不稳 | 每次指标跑 3 轮取均值，报告标注方差 |
| 重构面过大导致项目不可运行 | 面试现场翻车 | 每期结束保证 `main` 可跑 + 单测全绿；新编排层用 feature flag 切换 |
| 积分与真实计费脱节 | 讲不深 | 显式说明「充值占位」边界，重点讲**计量与一致性**而非支付集成 |
| 时间不足 | 半成品 | 按「可独立交付」切分：M0/M1 单独就有价值 |
