## 1. AI / 大模型相关

### LLM（大语言模型）

**全称**：Large Language Model（大语言模型）

**通俗解释**：
LLM 是一个"读过亿本书的 AI"，你给它一段文字（Prompt），它会接着写下一段合理的文字。
它能写文章、翻译、答题、生成代码 —— 本质上都是"接着写文字"。

**类比**：LLM 像一个"超级能聊天的图书管理员"。你问它问题，它不是去书架翻书，
而是基于它读过的所有书，"猜"出一个最可能的回答。

**为什么叫"大"**：参数（可以理解为"神经元"）数量巨大（几十亿到几万亿）。
参数越多，能记住的知识和模式就越多。

**项目用到的 LLM**：
- DeepSeek V4 Flash（默认）—— 又快又便宜
- DeepSeek V4 Pro（报告场景）—— 更准但慢
- Qwen3.8 Flash（备份）—— 阿里云的模型

---

### DeepSeek / Qwen

**DeepSeek**：中国 AI 公司"深度求索"出品的 LLM。V4 系列是较新版本，特点是中文能力强、便宜、开源。

**Qwen（千问）**：阿里云出品的 LLM 系列，也叫通义千问。Qwen3.8 是其最新系列。

**项目里的角色**：
- DeepSeek Flash：负责出题、追问、评分（高频，对延迟敏感）
- Qwen Flash：作为 DeepSeek 的备份（不同厂商，一家挂了还有另一家）

---

### Embedding（向量嵌入）

**通俗解释**：
把一段文字（比如"猫")变成一串数字（比如 `[0.1, -0.3, 0.7, ...]`，通常是 1024 个数字），
这串数字叫"向量"。语义相近的文字，向量也相近。

**类比**：
想象把每句话在脑子里"打分"：
- "猫"向量 ≈ [0.1, 0.2, 0.8, ...]
- "狗"向量 ≈ [0.15, 0.25, 0.75, ...]（和"猫"很接近，因为都是宠物）
- "汽车"向量 ≈ [-0.5, 0.6, 0.1, ...]（和"猫"差很远，因为完全不同）

计算机不会"理解"文字，但它会算两个向量的距离（余弦相似度）。
距离近 = 语义相近；距离远 = 语义不相关。

**本项目用的 Embedding 模型**：bge-m3（BAAI 智源出品），输出 1024 维向量。

---

### bge-m3 / bge-reranker

**bge**：BAAI General Embedding，智源研究院开源的 Embedding 模型系列。

**bge-m3**：
- 多语言（中文、英文、代码都能处理）
- 1024 维向量
- 单次 ~210ms，批量更快

**bge-reranker-v2-m3**：
- 精排（rerank）模型，不是 Embedding
- 把 (query, 文档) 拼起来一起编码，能更准地判断相关性
- 单次 ~180ms，比 Embedding 慢但精度更高

**类比**：
- bge-m3 像图书馆的"快速索引" —— 把书按大致主题归类
- bge-reranker 像"专业书评人" —— 真的读一遍，给出精确评分

---

### RAG（检索增强生成）

**全称**：Retrieval-Augmented Generation（检索增强生成）

**通俗解释**：
LLM 不知道自己公司有什么资料。RAG 的做法是：
1. 先去资料库里搜相关内容（检索）
2. 把搜到的内容塞给 LLM（增强）
3. LLM 基于这些真实资料回答（生成）

**类比**：
普通 LLM 答题 = 闭卷考试（全靠记忆）
RAG 答题 = 开卷考试（先翻书，再答题）

**为什么需要 RAG**：
1. LLM 不知道你的私有知识（公司文档、产品手册）
2. LLM 知识有截止日期
3. RAG 让回答"有据可查"，减少幻觉（LLM 一本正经胡说）

**本项目 RAG 流程**：
```
用户问："Redis 缓存穿透怎么解决？"
   ↓
检索（向量 + BM25 双路）→ 找到 3 篇相关文章
   ↓
精排（bge-reranker）→ 重排这 3 篇
   ↓
把最相关的塞给 LLM（拼成 prompt 的一部分）
   ↓
LLM 基于这些资料回答（不是凭空编）
```

---

### BM25

**全称**：Best Matching 25（最佳匹配 25）

**通俗解释**：
经典的"关键词搜索"算法。
"BM25 检索 Docker"会优先返回含"Docker"关键词多的文档，
而"向量检索 Docker"会返回语义相关但不一定含"Docker"的文档。

**类比**：
- BM25 像"按书名找书"（必须包含关键词）
- 向量检索像"按内容简介找书"（意思对就行）

**为什么两个都用**：
向量擅长理解语义，BM25 擅长精确匹配关键词。两者互补。

**项目里的实现**：
- 中文分词用 jieba（最流行的中文分词库）
- 索引重建在后台线程池（避免阻塞事件循环）

### 双塔 vs Cross-Encoder

**双塔（Bi-Encoder）**：
两个独立的"塔"（神经网络），分别把 query 和文档编码成向量，
然后比对两个向量的距离。

```
Query "Docker"  → [塔1] → 向量 [0.1, 0.5, ...]
                              ↘ 余弦距离
Document       → [塔2] → 向量 [0.2, 0.6, ...]
```

**优点**：文档可以提前算好向量存起来，搜索时只算 query 向量，极快
**缺点**：query 和文档分开编码，丢掉了两者之间的细粒度交互
（比如否定、条件、数字）

**Cross-Encoder（交叉编码器）**：
把 query 和文档**拼起来**一起过模型：

```
[Docker] + [容器与镜像的区别]  → [一个模型]  → 分数 0.92
[Redis]  + [容器与镜像的区别]  → [一个模型]  → 分数 0.15
```

**优点**：能捕捉细粒度差异，精度高
**缺点**：每次都要算一遍，无法预存

**项目里的策略**：先用双塔快速召回 20 篇，再用 Cross-Encoder 精排到 5 篇

### RRF / score_norm

**融合（Fuse）**：
两路检索（向量 + BM25）各自返回一组结果，需要合并成最终排名。

**RRF（Reciprocal Rank Fusion，倒数排名融合）**：
按名次的倒数加权求和：
```
vector 第 1 名 → 1/(60+1) = 0.0164
BM25   第 1 名 → 1/(60+1) = 0.0164
总分 = 0.0164 × vw + 0.0164 × bw
```

**优点**：不需要归一化分数，只看名次
**缺点**：忽略了分数差异

**score_norm（分数归一化融合）**：
先把每路分数归一化到 [0,1]，再加权求和：
```
vector 分数 0.92 → 归一化 1.00
BM25   分数 18.5 → 归一化 0.65
总分 = 1.00 × 0.5 + 0.65 × 0.5 = 0.825
```

**优点**：保留分数差异，更细粒度
**缺点**：归一化方式对结果敏感

**项目实测**：多学科场景下 score_norm 略优，但差别不大。

### LLM-as-judge

**通俗解释**：
用 LLM 当裁判，给模型输出打分。
比如让 DeepSeek 评价另一个 LLM 出的题"是否清晰"（0/1/2 分）。

**类比**：
学生作文写完了，请另一个 AI 老师来打分。
比自己（学生）打分客观，比请真人打分便宜。

**注意点**：
- LLM 评分有偏（倾向于给高分 / 编造理由）
- 项目用 temperature=0 + 严格 JSON schema 减少偏倚
- 实证：M4 评测 27 条样本中 100% 通过率，可信

---

### Token

**通俗解释**：
LLM 不直接处理"字"或"词"，而是处理 token。
大致：
- 1 个汉字 ≈ 1.5 token
- 1 个英文单词 ≈ 1.3 token
- 1000 token ≈ 750 个汉字

**为什么按 token 计费**：
LLM 的算力消耗与 token 数成正比，所以按 token 收费。

**本项目费用**：
- DeepSeek Flash：¥1/百万输入 token，¥2/百万输出 token
- 出 1 道题 ~ 600 token ≈ ¥0.001
- 跑完所有评测 ~ 60K token ≈ ¥0.06

### Prompt（提示词）

**通俗解释**：
你发给 LLM 的那段文字（"请扮演面试官"+"题目信息"+"要求"）。

**类比**：
Prompt 就像给员工的邮件 —— 写得越清楚、越具体，回复质量越高。

**本项目的 Prompt 模板**：
```
你是面试官__TITLE__，正在主持面试。现在要出第 __CUR__/__TOTAL__ 题。

题目信息：
- 主题: __TOPIC__
- 题型: __QTYPE__
- 难度: __DIFFICULTY__

要求：
- 口语化、像真实面试官提问
- 不超过 120 字

输出严格 JSON：{"question": "题目", "is_followup": false}
```

---

### 思维链 / 思考模式

**通俗解释**：
LLM 在给最终答案前，先在内部"自言自语"一段推理过程：
"用户问的是 X，X 涉及 Y，Y 的关键是 Z... 所以答案是..."
这段"自言自语"就是思维链。

**类比**：
- 不开思维链：抢答题，按铃就答
- 开思维链：先在草稿纸上写一遍推理，再给最终答案

**坑**：
DeepSeek V4 默认开思维链，但 max_tokens 小的时候会被思维链吃完，
最终答案反而是空字符串。项目里默认关闭，且 max_tokens 低于阈值强制关闭。

## 2. 后端 / Python 相关

### FastAPI

**通俗解释**：
一个现代 Python Web 框架，特点是：
- 自动生成 API 文档（Swagger）
- 原生支持异步（async/await）
- 类型安全（基于 Python 类型注解）

**类比**：
- Flask：老式便利店（够用但功能少）
- Django：大商场（功能全但重）
- FastAPI：新式便利店（快、现代、轻量）

**例子**：
```python
from fastapi import FastAPI
app = FastAPI()

@app.get("/hello/{name}")
async def hello(name: str):
    return {"message": f"Hello {name}"}
```
访问 `/hello/world` 返回 `{"message": "Hello world"}`

---

### asyncio（异步 I/O）

**通俗解释**：
"不等待"的编程方式。
传统编程（同步）：发请求 → 等待响应 → 收到后再发下一个（CPU 在等待时啥也不干）
异步编程：发请求 → 切去做别的事 → 响应回来再处理（CPU 一直在干活）

**类比**：
- 同步：你点一杯咖啡，站着等做好，再点下一杯
- 异步：你点 10 杯咖啡，都点完，等叫号时一起取

**为什么 LLM 应用必须异步**：
LLM 调用动辄 1-2 秒。同步的话，一个用户等 1 秒，CPU 闲置 1 秒；
异步的话，100 个用户同时等，CPU 在等 IO 的间隙处理别的请求。

**项目里的体现**：
所有 LLM 调用都是 `async def`，所有数据库查询都是 `async` 形式。

---

### contextvars（请求级隔离）

**通俗解释**：
每个 HTTP 请求都有自己独立的"小口袋"（contextvar），用于存放这个请求专用的数据，
不与其他请求混淆。

**类比**：
医院里每个病人有独立病历本。护士推车经过多个病人，但每个护士只会翻对应病人的病历。

**为什么需要**：
LLM 应用通常用请求头来传一些参数（如 trace_id），contextvars 让这些参数
"自动跟着请求走"，不用每个函数都传一遍。

**注意**：本项目已取消 BYOK，contextvars 主要用于 trace_id 隔离。

---

### SQLite WAL

**全称**：Write-Ahead Logging（预写日志）

**通俗解释**：
SQLite 默认模式下，写操作会锁整个数据库（读也阻塞）。
WAL 模式：写操作写到日志文件，读依然能读旧数据，互不阻塞。

**类比**：
- 普通模式：老师在黑板上改作业，所有学生都得等他改完才能看
- WAL 模式：老师在草稿纸上改，正本黑板继续给学生看，老师改完再同步过去

**本项目的策略**：
- 开发环境用 SQLite WAL（无外部依赖）
- 生产环境用 MySQL（更强的并发能力）

---

### 连接池（Pool）

**通俗解释**：
数据库连接很贵（建立连接要 TCP 握手 + 鉴权，几十 ms）。
连接池提前建好 N 个连接，请求来了直接拿走一个，用完归还。

**类比**：
租车行：提前停着 20 辆车，客人来了直接开走，用完还回来。
比每个客人来现造一辆快得多。

**本项目配置**：
- pool_size=20：常驻连接
- max_overflow=40：高负载时最多再加 40 个
- pool_recycle=3600：每个连接用满 1 小时就重建（防数据库服务端单方面断连）

---

### JWT

**全称**：JSON Web Token

**通俗解释**：
登录后服务端签发的一串"凭证"，客户端每次请求都带着它。
服务端不用存"用户登录状态"（无状态），只验证 JWT 是否合法。

**类比**：
酒店房卡 —— 服务员刷一下就知道你是哪个房间的，不需要前台打电话查。

**本项目使用场景**：
MAOO 平台登录后给前端 JWT，前端每次请求带 `Authorization: Bearer xxx` 头。

---

### SSE（Server-Sent Events）

**全称**：Server-Sent Events（服务器推送事件）

**通俗解释**：
服务器能主动给客户端推数据（不用客户端反复问）。
适合"LLM 流式输出"——字符一个一个推出来，用户能看到打字机效果。

**类比**：
- 传统 HTTP（请求-响应）：问一句答一句
- WebSocket：双向实时通话（像微信语音）
- SSE：单向直播（像视频网站推流）

**为什么本项目用 SSE 而非 WebSocket**：
- LLM 输出是单向的（服务端 → 客户端）
- SSE 走 HTTP 协议，更容易跨代理、跨防火墙
- 断连重连简单（带 `Last-Event-ID` 头续传）

### CORS

**全称**：Cross-Origin Resource Sharing（跨域资源共享）

**本项目**：
后端 FastAPI 设置了 CORS 允许前端域名（开发环境 `localhost:5173`，生产环境是前端实际域名）。

### MySQL

**通俗解释**：
最流行的开源关系型数据库（RDBMS）。
把数据存在"表"里，表之间有"关系"（外键）。

**类比**：
Excel 多张表的加强版 —— 多用户并发、安全、支持海量数据。

**本项目**：

- 通过 asyncmy 驱动异步访问
- 表包括：users / documents / vectors / score_records

---

### Redis

**通俗解释**：
内存数据库（数据存内存里），读写都是微秒级。
通常用作"缓存"或"短期记忆"。

**类比**：
- MySQL = 仓库（东西全、慢）
- Redis = 办公桌（常用的放桌上，伸手就拿）

**本项目用法**：
1. 限流计数器
2. 短期会话状态（24h TTL）
3. 跨 worker 通信（如分布式锁预留）

---

### Sentinel

**通俗解释**：
Redis 的高可用方案 —— 主从自动切换。
主 Redis 挂了，从 Redis 自动顶上，业务几乎无感。

**类比**：
企业双电源 —— 一路电源故障，另一路立即接管，机房不会断电。

**本项目**：
代码已支持 Sentinel 配置（生产部署可启用，单机开发不需要）。

## 5. 算法 / 数据结构

### 滑动窗口

**通俗解释**：
限流算法 —— 在一个"时间窗口"内只允许 N 个请求。
滑动 = 窗口随时间向后滑，新请求进来时旧的过期掉。

**类比**：
高速公路限速 —— 不是"一天最多 1000 辆车"（固定窗口），
而是"任意 1 分钟内最多 60 辆车"（滑动窗口）。

**本项目实现**：
用 Lua 脚本 + Redis ZADD 维护滑动窗口，O(1) 内存。

### 熔断器 / 三态熔断

**通俗解释**：
电路保险丝的逻辑版。
- **closed（关闭）**：正常调用
- **open（断开）**：连续失败多次后，暂时不调用，直接拒绝
- **half-open（半开）**：过一会试一次，成功就恢复，失败就继续断开

**类比**：
- 你给手机充电 —— 充电头坏过 3 次（open），你就不敢再用这个充电头
- 过两天看到新批次（half-open），试一次
- 没炸（成功），重新放心用（closed）

**本项目实现**：
每个模型独立一个熔断器，记录连续失败次数，达到阈值断开。

### 幂等性

**通俗解释**：
同一个请求执行 1 次和执行 N 次，效果相同。
（积分只扣一次、消息只发一次，不会因为重试而重复扣费。）

**类比**：
- 取款：幂等操作（账户余额减少，不会因为重复操作变两倍少）
- 发短信：不幂等（重发 3 次就发 3 条）

**本项目**：
- 积分扣费：`幂等键 = (request_id, kind)`，同一请求只扣一次
- 充值：`幂等键 = order_id`，同一订单只入账一次

## 6. 部署 / 运维

### Docker

**通俗解释**：
把应用 + 依赖 + 系统库打包成一个"镜像"。
任何机器装了 Docker 都能跑同一个镜像，**环境完全一致**。

**类比**：
外卖便当 —— 厨房（你的电脑）做好打包，送到哪都能吃，
不用管收外卖的人家厨房什么样。

**本项目**：
backend / frontend 都做了 Docker 镜像。

---

### docker-compose

**通俗解释**：
Docker 的多容器编排工具。
一个 yaml 文件定义多个容器（mysql、redis、backend、frontend），
一键起停。

**本项目**：
`docker-compose.yml` 在项目根目录，`docker compose up` 拉起全部服务。

---

### 多实例部署

**通俗解释**：
同一份代码跑多个进程（worker），前面接负载均衡（nginx）把请求分散。
单进程扛不住，多进程就能扛。

**类比**：
一家小店 → 连锁店。单店只能服务 10 个客人，连锁 10 家能服务 100 个。

**本项目**：
gunicorn 启动多个 uvicorn worker 进程，单机即可横向扩展。

---

### gunicorn / uvicorn

**gunicorn**：Python 的 WSGI 应用服务器，用来跑多个 worker 进程。

**uvicorn**：ASGI 应用服务器，原生支持 asyncio 和 WebSocket。

**本项目**：
用 gunicorn 当主进程 + uvicorn worker（既有多进程，又有 asyncio）。

## 7. 测试 / 质量

### pytest

**通俗解释**：
Python 最流行的测试框架。
用 `assert` 写断言，自动找测试函数，自动跑。

**类比**：
考试的自动阅卷机 —— 把答题卡放进去，自动判对错。

**本项目**：
63 个测试，5 分 29 秒全过。

---

### Mock（桩）

**通俗解释**：
测试时用"假的"组件代替"真的"组件。
比如测试时不真的去调 LLM（要花钱），而是用一个返回固定结果的 MockLLM。

**类比**：
考试时老师给你一份"标准答案"对照，不需要真的去查资料。

**本项目**：
`MockLLM.chat()` 根据 prompt 关键字返回固定 JSON，不真的调外部 API。

---

### e2e（端到端测试）

**全称**：End-to-End（端到端）

**通俗解释**：
测完整流程，不是单元。
e2e 测试：模拟用户从打开网页 → 答题 → 拿到评分，看整个链路是否通。

**类比**：
- 单元测试：测一个零件
- 集成测试：测几个零件装起来
- e2e 测试：测整个机器能不能跑

**本项目 M5**：
练习模式 9 个检查点 + 模拟面试 7 个检查点 = e2e 冒烟。

## 8. 业务 / 产品 相关

### BYOK

**全称**：Bring Your Own Key（自带密钥）

**通俗解释**：
让用户自己提供 LLM API Key。
好处：用户付钱，平台不背成本。
坏处：用户体验差（要去申请 key）、密钥泄露风险、平台无法控制质量。

**本项目决策**：
**取消 BYOK**！改为平台统一提供 key + 积分扣费。
用户更省事，平台能控制成本和质量。

---

### MAOO

**全称**：无（这是项目用户当前使用的部署平台名，平台名为 maoojjkk.xyz）

**通俗解释**：
类似于 "阿里云" 或 "腾讯云" 的 PaaS 平台，
提供应用托管、用户管理、数据库托管等基础能力。

**本项目与 MAOO 的关系**：
- 用户系统走 MAOO（maoo_user_id 关联）

- 通过 `PlatformAdapter` 抽象层解耦

## 9. 容易混淆的术语速查表

| 容易混的 | 区别 |
|---|---|
| **同步 vs 异步** | 同步 = 排队；异步 = 一起办 |
| **进程 vs 线程 vs 协程** | 进程 = 独立程序；线程 = 进程内子任务；协程 = 更轻量的"线程"（asyncio 用）|
| **前端 vs 后端** | 前端 = 网页（用户看到的）；后端 = 服务器（处理逻辑）|
| **向量 vs 关键词** | 向量 = 语义相似；关键词 = 字面相同 |
| **召回 vs 精排** | 召回 = 粗筛（快、广）；精排 = 精挑（慢、准）|
| **session vs token vs cookie** | session = 服务器记的状态；token = 无状态凭证；cookie = 浏览器存的小文件 |
| **QPS vs TPS vs 并发** | QPS = 每秒查询数；TPS = 每秒事务数；并发 = 同时处理数 |
| **Docker vs 虚拟机** | Docker 共享内核（轻）；虚拟机独占内核（重）|
| **JWT vs Session** | JWT 客户端存凭证；Session 服务端存状态 |
